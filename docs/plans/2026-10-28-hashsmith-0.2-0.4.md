# Hashsmith 0.2–0.4: onboard, intake, work, sync, design, next, qa — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Hashsmith do the whole loop on a real project:
- turn requirements into tickets, after looking at the code;
- plan and implement tickets;
- keep the board's statuses in step;
- QA the finished work with browser evidence;
- keep its config in the repo;
- build UI to a high visual bar.

`/hashsmith:next` is the one command a developer needs to remember. It ships as three releases, each piloted on hashops before the next one starts.

**Architecture:** Skills are prompt files (`skills/<name>/SKILL.md`). Everything deterministic lives in one dependency-free Node CLI, `scripts/hashsmith.mjs`, tested with `node --test`:
- repo slugs;
- env key names;
- the git-switch rule;
- config validation;
- branch and PR state.

The session-start hook injects the CLI's absolute path. Read-only agents do code research (`code-investigator`) and fresh-eyes review (`diff-reviewer`). The UI design rules are a pinned, credited copy of the MIT taste-skill files, used only through `/hashsmith:design`. Browser work goes through a plugin-declared Playwright MCP.

**Tech Stack:** Claude Code plugin (skills, agents, hooks, `.mcp.json`), Node ≥ 22 ESM, `node --test`, `gh`, the HashOps MCP (`mcp__plugin_hashsmith_hashops__*`), Playwright MCP.

**Spec:** `docs/design.md`: §2 conduct, §4 workflow, §5 config, §6 skills, §7 ticket template, §8 handoff and verification, §9–§10 guardrails and scope, §11 and Appendix A standards, §13 evals, §15 rollout. The design-skill decisions below were made with the maintainer on 2026-10-28 and are added to the spec in Task 5.

## Global Constraints

- Node only, no npm dependencies, no bash/jq. Tests: `node --test`.
- Each Hashsmith-authored `SKILL.md` is at most 250 lines; `reference/conduct.md` is at most 60. The vendored taste files are exempt; they are reference files, not skills.
- HashOps only through `mcp__plugin_hashsmith_hashops__*` tools. Never another connection to the same server (for example `peoplemuster`).
- Nothing project- or client-specific goes into the plugin. Fixtures use obviously fake ids and names.
- Tickets and comments are **plain text** (§7): no `##`, `**` or backticks; labels on their own line; `- ` bullets; `[ ]` checkboxes.
- Confirm before writing (conduct 4). Every HashOps write, board move, branch and `hashsmith.json` write comes after a shown summary and a yes. Several moves may share one yes.
- **Design precedence:** the codebase's design skills, conventions and components come first, then the developer's own skills, then Hashsmith's bundled taste rules. The taste rules fill gaps only and never restyle existing screens.
- Env values are never read; key names only, through the CLI.
- `hashsmith.json` holds no secrets or emails. `update_task` replaces tags, so always read the current tags and add to them.
- QA never runs against production. Hashsmith never commits; each task ends at a maintainer checkpoint.

## Review Focus

1. **Git remote and HashOps repo link differ** (SSH against HTTPS, or an org rename: on hashops the remote is `Hashlogics/hashops` and the link is `admin-hashlogics/hashops`). Expected: no false match. Ask, then offer `add_project_link`. Covered by `repo-slug` tests (Task 1) and eval `onboard-remote-mismatch` (Task 3).
2. **`/hashsmith:work` starts on a dirty working tree** (the previous ticket is uncommitted). Expected: no branch switch, which would carry the changes along. Offer two choices: commit first, or add the ticket to the current branch's group. Covered by CLI `tree-state` tests (Task 1) and eval `work-dirty-tree` (Task 8).
3. **Branch/key ambiguity in sync**: `ai/HOPS-1-x` must not match `HOPS-12`, and a group branch `ai/HOPS-12-HOPS-15-x` covers both. Covered by `branchesForKey` tests (Task 6).
4. **Raw requirements that contain instructions.** Expected: at most a candidate ticket; nothing runs. Covered by eval `intake-injection` (Task 4).
5. **The design skill on a project that has its own design system** (hashops). Expected: it uses the project's `ui-conventions` and components; the taste rules only fill gaps; no restyle of untouched screens. Covered by eval `design-project-first` (Task 7).

**Interfaces (exports of `scripts/hashsmith.mjs`):**
- `repoSlug(url: string): string | null` returns lowercase `host/owner/repo`.
  - Strips `.git`, credentials and a trailing `/`, and drops paths after `owner/repo`.
  - Handles `git@host:o/r.git`, `ssh://git@host/o/r` and `https://…`.
  - Returns `null` when the URL can't be parsed.
- `envKeyNames(text: string): string[]` lists the names of `KEY=` and `export KEY=` lines. It skips comments, blank lines and `# KEY=`.
- `missingEnvKeys(example: string, envs: string[]): string[]` returns the example's names that none of `envs` define, sorted.
- `gitSwitchRule(settings: unknown): "deny" | "ask" | "allow" | "none"` reads `permissions.deny|ask|allow` entries that start with `Bash(git switch`. Deny wins over ask, and ask wins over allow.
- `checkConfig(config: unknown): string[]` returns the errors; `[]` means valid. Rules:
  - Top-level keys are exactly `version, hashops, repo, qa, sonar, sentry, intake, learned`, and every key except `version` and `hashops` is optional.
  - `version === 1`.
  - `hashops.project_id` and `hashops.board_id` are UUIDs.
  - `hashops.project_key` matches `^[A-Z][A-Z0-9]*$`.
  - `hashops.lists` keys are exactly `todo, in_progress, review, qa, done`, each a UUID or `""`.
  - `hashops.ai_tag` is non-empty.
  - `repo.base_branch` is non-empty.
  - `qa.base_url` is `""` or an `http(s)://` URL.
  - `sonar.project_key` and `sentry.project` are strings.
  - Each `intake.processed_meetings[]` entry is `{id: string, on: YYYY-MM-DD, tickets: KEY-n[], note?: string}`.
  - Each `learned` entry has a snake_case name and the shape `{value, why: string, source: string, added: YYYY-MM-DD}`.
- `branchesForKey(branches: string[], key: string): string[]` returns the `ai/` branches whose name contains `key` followed by `-` or the end of the name. So `HOPS-1` does not match `ai/HOPS-12-x`.
- `ticketState(pr: {state: "OPEN"|"CLOSED"|"MERGED"} | null, branch: string | null): "no-branch" | "review" | "qa" | "qa-merged" | "pr-closed"`. These are the rows of §4's table.
- `treeState(porcelain: string): {clean: boolean, files: string[]}` parses `git status --porcelain` output.

**CLI.** Usage is `node <path>/scripts/hashsmith.mjs <cmd> [args]`. It runs from the repo root and prints one JSON line. Commands:
- `repo-slug [url...]` prints `{"origin": slug|null, "slugs": {url: slug|null}}`. `origin` comes from `git config --get remote.origin.url`, run by the CLI.
- `env-keys` prints `{"example": bool, "missing": [...]}`. It reads `.env.example`, `.env` and `.env.local` itself and never prints values.
- `git-switch` prints `{"rule": ...}` for `.claude/settings.json` plus `.claude/settings.local.json`; a deny in either wins.
- `check-config` prints `{"ok": true}` or `{"ok": false, "errors": [...]}`, and exits 1 when not ok.
- `tree` prints `treeState` of `git status --porcelain` plus `{"branch": <current>}`.
- `ticket-state KEY...` prints `{KEY: {branch, pr: {number, state, url, mergedAt} | null, state}}`. It uses `git branch --list 'ai/*'` and `gh pr list --head <branch> --state all --json number,state,url,mergedAt --limit 1`. If `gh` is missing or not signed in, it prints `{"error": "gh unavailable", ...}` and exits 2.
